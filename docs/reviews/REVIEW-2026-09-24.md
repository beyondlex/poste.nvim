## Bugs fixed

1. **A directive-lookalike line inside a multi-line literal was deleted**
   (`poste-core/src/sql_parser.rs`, `poste-cli/src/exec_file.rs`, `3f85f2e`).
   `strip_directives` filtered by line alone: any line matching
   `^\s*--\s*@w+` was dropped, wherever it stood — including INSIDE a
   multi-line string literal, where such a line is data:

   ```sql
   INSERT INTO notes VALUES ('line one
   -- @database sample
   line three');
   ```

   The server received a two-line value; a `DO $$ … $$` body lost a
   comment-shaped line inside it. Both entry points that strip directives
   (`exec-file`'s own copy and the request path via
   `split_statements_with`) shared the flaw, and the two copies had drifted
   into existence in the first place — the duplication was the smell.

   `strip_directives` is now literal-aware: a line is strippable only when
   it starts outside every literal, decided by a scanner mirroring
   `split_statements_with`'s grammar (single-quoted strings with `''`
   doubling, double-quoted / backtick identifiers, `$tag$` / `$$` bodies,
   `--` line comments — where a quote is just text, so `-- don't` cannot
   open a fake literal that blinds the scan — and `/* */` blocks). The
   core function is `pub` and exec-file calls it; its `###` separator
   filter stays local. 5 regression tests pin the multi-line string, the
   doubled-quote continuation, the dollar-quoted body, the apostrophe-in-
   comment trap, and every previously-strippable top-level shape.

2. **Found and fixed on the way: the scanner's own off-by-one.** The
   `$`-tag arm set `i = j` (past the opening tag) and then fell through to
   the loop's generic `i += 1`, swallowing one extra character — for
   `$$\n…` that is the newline, whose line-start flag was never pushed and
   whose line was silently dropped from the zip with `lines()`. Caught by
   the dollar-quoted regression test before it could ship; the arms that
   consume a variable number of characters now all `continue` explicitly.

## Verified clean rather than assumed

- **The `\xHH` escape fix has no Rust counterpart** (poste-redis's
  `fc6e575`): the binary receives argv, never file text — `\xHH` decoding
  happens (correctly) only in the Lua tokenizer.
- **`mask_url_password` splits userinfo at the FIRST colon** and
  `looks_like_credentials` treats an all-digit tail as a port — re-read
  against `u:pa:ss@h` and a numeric password; both hold.
- **`replace_database_in_url`** keeps the query/fragment (`?sslmode=`),
  handles no-path URLs (`postgres://host` → `host/newdb`), and leaves
  sqlite URLs (no `://`) untouched — re-derived from the source, not from
  the doc.

## Recorded, not changed

- The `###` separator filter in `exec-file`'s strip is still line-based:
  a line that is exactly `###` inside a multi-line literal would be
  dropped. The directive fix carries the literal-aware scanner; extending
  it to the separator means pushing an option through the core function
  for a shape only mixed .rest/.sql files produce — recorded, not built.
- `split_statements_with` does not nest block comments (`/* /* */ */`
  ends at the first `*/`); Postgres nests them. Matching servers on this
  costs a depth counter in a hot path for a construct that appears in
  generated SQL roughly never.
