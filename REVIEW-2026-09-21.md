# Code Review — 2026-09-21

Follow-up to `REVIEW-2026-09-20.md`. This pass stayed on the connection-store
mirror contract and did what the 09-20 pass could not: compared the two
implementers field by field for the `port` entry specifically, then checked
which of this day's Lua-plugin findings (`poste-db` and `poste-redis`
`REVIEW-2026-09-21.md`) have a Rust counterpart at all. Baseline:
`cargo test --workspace` green (479 → **483** with this pass's additions),
clippy `--workspace --all-targets -- -D warnings` 0 warnings, fmt clean.

## Bugs fixed

1. **`port` was never expanded, and barely validated** (`sql_connection.rs`,
   `f2a5948`). The store parsed `port` with `u16::try_from` at load time and
   then substituted `{{VAR}}` references into host/user/password/database/path
   — not `port`. Lua's `apply_env` substitutes *every* field before validating
   any of them, so `port = "{{DB_PORT}}"`, a config the editor honours, lost
   its value here and connected to the dialect default; `port = 0` fitted a
   `u16` and reached the URL as `…:0/…`. `port` now keeps its raw text
   (`ConnectionConfig::port_raw`) whenever it is not already a usable number,
   and `parse_port` accepts exactly what Lua's `tonumber` + integrality +
   1..65535 check accepts (`"5432.0"` in, `"5432.5"`, `"abc"`, `0`, `70000`
   out). An unparseable value fails *that connection* at resolve with the
   message naming it — the Lua resolver scopes it the same way, and one typo'd
   stanza taking down every other entry in a shared file would be the worse
   bug. The value stays out of the message: `port = "{{POSTE_PASS}}"` is a
   plausible typo and this reaches a terminal.

2. **Two hand-copied substitution lists** (`ConnectionStore::resolve` and
   `poste-cli/src/connection.rs`'s `connection test`). Identical five-line
   blocks, and the drift that the duplication invites had already happened in
   the one direction that mattered: neither list included `port`, so
   `connection test` would have checked the default port even after `resolve`
   was fixed. Both now call one `ConnectionConfig::with_vars_resolved`, which
   returns the resolved config (so `test` can hand it to `test_connection`) or
   the port error.

3. **The legacy `connections.json` accepted port 0** (`sql_connection.rs`,
   `82cc1c4`). There `port` is a serde-typed `u16`, so `70000` and `"abc"`
   failed the load but `0` passed straight into `mysql://h:0/`. The load now
   defers it to the same resolve-time check the TOML path uses, so both files
   answer a bad port identically: an error naming the connection.

## Verified this pass

- The three headline Lua findings of this day have **no** Rust counterpart,
  checked rather than assumed: the SCAN at-least-once dedup —
  `redis_executor.rs` maps one round-trip's `[cursor, items]` into JSON and no
  loop accumulates across cursors (the only `cursor` hits in `poste-core` are
  the editor cursor in the SQL-context tokenizer), so every accumulator that
  needed dedup is Lua; the destructive-command gate — the only `confirm` in
  the tree is AMQP publisher confirms (`mq_executor.rs:246`), no SQL gate
  lives in the binary; the quoted command-head blacklist bypass — there is no
  `.redis` command tokenizer on this side to bypass.
- `docs/schema.md`'s mirror list now states the `port` rule (expand the
  reference, then bound it), so the next drift is a written-down violation
  rather than a surprise. The 09-20 field-by-field comparison of `to_url()` vs
  Lua `build_conn_url` (percent-encode sets, alias tables, auth shapes,
  sqlite `?mode=rwc`) is unaffected by this change.

## Recorded, not changed (with rationale)

- **`ConnectionStore::load` has no cache at all** — it re-reads and re-parses
  `connections.toml` per invocation, so the whole `getftime` second-granularity
  staleness class that the Lua plugins carry does not exist here. Making it
  faster would import that class; not worth it for a CLI.
- **`to_json_list` reports `port: null` while a reference is pending** — the
  listing shows no port rather than `{{DB_PORT}}`. Echoing the raw text would
  put a possibly-secret reference on screen for a display-only field.
- **A legacy JSON file with any unreadable `port` fails the whole load** (the
  serde path, not the deferred value): `port` there is typed `u16`, so
  `"abc"` errors at parse. Documented-legacy format, and the TOML path — the
  one the plugins actually write — is per-connection.

## Round 2 — the CLI's URL rules and statement classification

Same day, second pass, upstream-to-downstream this time: how a resolved
connection URL is *read* (`exec-file`, `session`, `introspect`), what those
paths print when they cannot read it, and how a statement is classified.
Baseline for the round: 483. After: **487 passed / 0 failed**, clippy
`--workspace --all-targets` 0 warnings, `cargo fmt --check` clean.

4. **Three copies of the URL-scheme rule, already drifted, and `mariadb://`
   in none of them** (`poste-core/src/request.rs`, `a3ea26b`). `exec_file.rs`,
   `session.rs` and `introspect.rs` each hand-rolled the same
   `starts_with` chain. They disagreed on the failure mode — exec/session
   bail, introspect answered `"postgres"` for *anything* it did not recognise,
   including a `redis://` URL, which then died inside the postgres driver with
   a message about a URL that never claimed to be one. Worse, Lua's
   `constants.URL_SCHEMES` (whose own comment names these three chains as its
   mirror) lists `mariadb://`, and sqlx's MySQL driver lists it too
   (`URL_SCHEMES = ["mysql", "mariadb"]`), so a legal
   `url = "mariadb://…"` entry was readable by the editor for display and
   session context yet failed the moment it ran. The chain is now one
   `Protocol::from_sql_url`, extended to cover `mariadb://`, with the three
   entry points calling it and introspect's silent postgres fallback removed.

5. **Every "cannot determine protocol" message printed the connection
   password** (`7d8984c`, `ba31fd1`, and the redis/mq/mssql/clickhouse
   validators). The CLI's `mask_url_password` was private to the `connection`
   subcommand, so the six other places that quote a resolved URL in an error —
   exec-file, session, introspect, the redis and AMQP validators, the mssql
   and clickhouse URL parsers — echoed it raw. Those URLs carry real
   credentials by construction, and a CLI error line reaches a terminal,
   `:messages`, and saved result files. The helper moved to `poste-core`
   beside the other URL rules and every one of those sites masks now.
   Moving it fixed a second defect: it scanned for `@` across the whole URL,
   so `postgres://db.example.com:5432/team@billing` — `@` is legal in a
   database name — lost its port and part of its name to the mask while
   hiding nothing. The scan is confined to the authority now, which the new
   test pins in both directions.

6. **A truncated redis string still shipped its full parsed body**
   (`redis_executor.rs`, `4d8a18d`). `max_bytes` cut `value`, then the JSON
   heuristic parsed the *untruncated* string and attached the whole document
   as `parsed`, so one large JSON value defeated the cap and re-appeared in
   stdout — the size class these caps exist to bound, because the Lua side
   reads line-delimited JSON and an oversized line stalls the job. `parsed` is
   now emitted only when the value fit. No consumer reads the field today
   (checked across all three Lua plugins), so the shape change is invisible
   except for the huge-value case.

7. **`RETURNING` matched as a substring, unlike the Lua mirror**
   (`sql_exec_common.rs`, `cca0b81`). `exec_run.lua` has used a
   `%f[%w_]returning` word-boundary test since it hit this exact case, and its
   comment names `my_returning_col`; the Rust copy kept
   `upper.contains("RETURNING")`. So `UPDATE orders SET returning_flag = 1`
   took the fetch branch: `fetch_all` runs the statement, but the outcome is
   reported with `is_dml: false, affected: 0` — an update that changed five
   rows displayed as "0 rows". Classification now matches whole words.

## Verified clean rather than assumed

- The Lua default-port rule is not the mirror bug it looks like.
  `const.default_port` does *not* normalize aliases, so `dialect = "postgresql"`
  would have reached `.. ":" .. port` as nil and thrown — except every entry
  point into `build_conn_url` (`get_connection_config`, `resolve_connection_url`,
  `name_for_url`, `list_connections`) applies `normalize_dialect` first, and the
  display fallback at `connections.lua:458` is fed the same normalized values.
  Confirmed by reading all four, not by the port table passing.
- The Rust/Lua percent-encoding sets agree: `USERINFO_ENCODE_SET` is CONTROLS
  plus every printable ASCII outside `A-Za-z0-9-._~`, i.e. the same RFC 3986
  userinfo rule the Lua encoder implements.
- `sql_ddl`'s `create_table` is the only member with a production caller (the
  four `sql_introspect` modules), and the two dialects whose `column_def_sql`
  ignores `comment`/`extra` (mssql, clickhouse) both pass `None` for those
  fields, so the silent loss is unreachable today. Documented in the code
  (`71c73c7`) instead of fixed for a caller that does not exist.

## Recorded, not changed (with rationale)

- **Six `DdlGenerator` members have no caller** (`add_column`, `drop_column`,
  `rename_column`, `alter_column_type`, `add_index`, `drop_table`): they exist
  since the initial commit as table-designer scaffolding, are exercised only
  by their own tests, and the browser's column actions build their ALTER SQL
  in Lua instead. Two of them are also subtly wrong — `add_column` routes
  through `column_def_sql`, so a caller that sets `comment` loses it on every
  dialect. Deleting them is the right call the next time this file is touched
  for a real reason; deleting them now would also delete the only tests that
  document each dialect's ALTER syntax.
- **Three copies of the default-port table**: `Dialect::default_port` (zero
  production callers), `ConnectionConfig::to_url`'s inline match (the live
  one), and Lua's `DIALECT_DEFAULT_PORTS`. All four values agree today, and
  `to_url`'s `_ => 1433` arm is only reachable for `mssql` because the outer
  match names the other three — adding a fifth network dialect there would
  silently inherit MSSQL's port. Worth collapsing onto `Dialect::default_port`
  when a dialect is actually added.
- **`introspect` now fails on an unknown scheme** instead of assuming
  postgres. Deliberate, and it only changes the message for inputs that were
  already broken.
- **`--max-items 0` renders nothing** rather than meaning "unlimited" the way
  `--max-rows 0` does. Lua never passes 0 (it either omits the flag or sends a
  positive cap), so the two zero-means differ without ever meeting.
