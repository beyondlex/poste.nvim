# Code Review — 2026-09-22

Follow-up to `REVIEW-2026-09-21.md`. This pass left the connection store and
turned to the redis transport — `poste-exec/src/redis_executor.rs`, the other
half of the reply-shape contract that `poste-redis/lua/poste-redis/format.lua`
renders. Picking that file for a bug hunt (rather than the next Lua module)
paid for itself: the shape it emits is only correct if the consumer agrees, so
each finding was checked against the Lua side in the same pass, and one of them
turned out to be a Lua bug wearing Rust clothes. Baseline:
`cargo test --workspace` green (483 → **494** with this pass's additions),
clippy `--workspace --all-targets -- -D warnings` 0 warnings, fmt clean;
poste-redis gate 598 → **602** passed / 0 failed / 0 errors, luacheck 0/0.

## Bugs fixed

1. **Both executors echoed the connection URL — password included — into their
   scheme-rejection message** (`redis_executor.rs`, `mq_executor.rs`,
   `1815f63`). `validate_connection_url` interpolated the raw URL, so a SQL
   entry pasted into a redis slot (or a redis entry into an AMQP one) printed
   `postgres://user:secret@host:5432/db` on the terminal and into the plugin's
   error panel. The rejection path is precisely where a live credential is
   most likely to be present: a wrong scheme happens when the user supplied the
   wrong connection, not a stale one. The masking helper was already written
   and tested, but as a *private* function in `poste-cli/src/connection.rs`
   used only by `connection list`. It moved to `poste_exec::url` so all three
   call sites share one implementation — the duplication was why the validators
   could silently lack it — and the CLI integration test now feeds a
   `postgres://alice:s3cret@x/y` URL through `redis exec` and asserts neither
   `s3cret` nor an unmasked URL appears on stderr. `url.rs` gained a
   bare-password case (`redis://:hunter2@host:6379/3`) that every inherited
   test missed: they all had a username before the colon, which is the shape
   `redis` actually allows and SQL URLs do not.

2. **A binary value inside a collection rendered as `(nil)`**
   (`redis_executor.rs`, `0cf4d60`). The `binary` shape has always carried
   `len`/`truncated` and *no* `value` key; hash rows and list elements built
   their cell by pulling the child's `value`, which is JSON `null` when the key
   is absent. So a msgpack/protobuf field, or any non-UTF-8 element, showed up
   as `(nil)` in a grid that simultaneously reported the row as existing. A
   string reply at top level had always shown the `(binary) N bytes hex: …`
   summary — the content existed, the nested path just dropped it. Binary now
   carries the same one-line summary as its `value`, and a new `child_cell`
   keeps a child's whole shape when it has no `value` at all, which is the
   other half of the same bug: a nested `hash` has `entries`, and flattening it
   to `null` hid a value that is very much there.

3. **A pair key the converter could not read as a string was dropped, while
   `len` kept counting it** (`redis_executor.rs`, `0cf4d60`). `key_string`
   returns `None` for anything that is not a bulk/simple string, and the
   hash/zset/stream/`Map` arms skipped the pair in that case. The visible
   symptom is a collection with fewer rows than its own reported total and no
   error — silent, and only reachable via RESP3 maps with typed keys, which is
   why it had survived. `key_display` now always yields text: decimal for an
   integer/double/boolean/big-number key, `hex:` for a non-UTF-8 field name
   (`key_string` would have shown a lossy string, i.e. one replacement char per
   byte, which is worse than useless as an identifier), and a named fallback
   for a nested key.

4. **`parsed` bypassed `--max-bytes` and duplicated the payload**
   (`redis_executor.rs`, `0cf4d60`). The JSON heuristic parsed the
   *untruncated* string, so a 200 MB JSON blob arrived capped to 64 KB *plus*
   its full parsed tree — the cap bounded only the display copy while the
   payload doubled. It is now skipped for a truncated value, which also
   removed the temptation to blame `serde_json` for the size: an intentionally
   truncated value cannot be reassembled, so parsing it was never available.

5. **RESP3-typed replies rendered as debug text** (`redis_executor.rs`,
   `0cf4d60`). RESP3 is opt-in (`?protocol=resp3` in the URL), so the whole
   `Set`/`Double`/`Boolean`/`BigNumber`/`VerbatimString`/`Attribute` region had
   no code path and no test. They fell into a catch-all `_` arm using
   `format!("{:?}", …)`, which meant a set read as `Set([...])` — and, before
   that, as a hash of "pairs" once the array path saw it — while `HGETALL`
   answered with `Double(1.5)` instead of `1.5`. Each now has its shape: sets
   stay sets (`items_shape` is shared with lists, since the pair-extraction
   branch was the thing mislabelling them), numbers/booleans/big integers print
   as values, verbatim strings as strings, and `Attribute` recurses through
   the metadata to the payload that was asked for. zset scores accept a
   RESP3 `Double` member score, which RESP2 never sent.

6. **`escape_for_line` returned `gsub`'s count as a second value, and it
   became a phantom panel row** (`poste-redis/lua/poste-redis/util.lua`,
   `3e6fcc0`). Found while pinning the Lua half of this contract: a new spec
   asserted one rendered line and got `123456789012345678901234567890` plus a
   second line containing `0`. `return s:gsub(…):gsub(…)` yields `(string,
   count)`; `format.lua` splices cells with `{ cell(value) }`, so the count
   landed as an extra table element that `table.concat` cheerfully rendered.
   Every other `gsub` site in the file was already parenthesized — this was the
   outlier, not the pattern. The fix is the parens; the test pins both the
   visible symptom (`#out.lines == 1`) and the cause
   (`select("#", escape_for_line(…)) == 1`), because a spec that only asserts
   the text would pass again the moment someone "simplifies" the return.

## Verified this pass

- Nothing on the Lua side reads `parsed`: the only `parsed` identifiers in
  `lua/` are unrelated locals (`context.lua`'s cache watermark, `cli.lua` and
  `connections.lua`'s decode results). So gating it on truncation cannot break
  a panel feature, which was the reason to check before shipping fix 4 rather
  than after.
- `doc-poste`'s redis configuration page already stated the rule fix 4
  implements ("截断后的值也不再附 `parsed` JSON"), written while describing the
  transport cap. The code did not honour it on the redis path until this pass —
  the doc was right and the implementation was behind it, which is the
  mirror-contract failure mode worth noticing: a prose rule nobody re-checks
  against both executors.
- `redact_url` exists in `util.lua`, and it cannot help here: by the time Lua
  has the message, the binary has already printed the credential. Redaction
  belongs in the process that composes the message — hence fix 1 lives in
  Rust, not in the Lua formatter.
- The `(nil)`-in-a-grid-row symptom is genuinely reachable from Redis, not just
  a synthetic unit test: `HSET blob \x80\x01 <msgpack>` is a legal field name
  and value, and RESP2 already returns bulk strings that fail UTF-8.
- An embedded NUL survives `nvim_buf_set_lines` (probed directly: a 3-byte line
  with a NUL round-trips through a buffer), so the hex preview is a display
  choice, not a crash guard — worth stating because it is the natural wrong
  explanation for the fix.

## Recorded, not changed (with rationale)

- **Non-UTF-8 field/member names show as `hex:…`, which is display-only**: you
  cannot paste it back into `HDEL`/`ZREM` as the real name. Making it
  addressable would need a binary-safe selection path through the grid, i.e. a
  feature; the old behaviour (row missing entirely) was worse than a name you
  can see but not reuse.
- **A zset score that parses to nothing becomes `0.0`** (`redis_executor.rs`'s
  score arm). Silent, but the alternative — dropping the member — is the bug
  fixed in item 3. Not a correctness problem under RESP2/RESP3 as Redis emits
  numeric scores; noted so the next reader does not "fix" it by skipping.
- **`ServerError`/`Push` still reach the debug-format `_` arm.** `ServerError`
  has no `Display` in redis 0.27.6 and `Push` is pubsub, which this transport
  does not subscribe to; there is no shape in the contract for either. A
  command error surfaces through `status: "error"`, not through the value, so
  the arm is a formatting oddity rather than a lost error.
- **`BigNumber`'s Rust arm is untestable without a new dev-dependency**: redis
  0.27.6 does not re-export `num_bigint::BigInt`, so no test can construct the
  variant. It is `n.to_string()`, and the wide-integer case is covered from the
  Lua side (`format_spec.lua`'s 30-digit assertion), which is where the
  contract is observable.
- **Renaming a grid row whose value is binary fails instead of corrupting**
  (`browser/tree.lua`'s rename path passes `row_data[3] or ""`, giving redis an
  arity error). Bad, but a visible error beats writing the wrong key; the
  `edit_cell` `input == current` guard already refuses the lossier
  round-trip.
- **lapin's `Connection::connect` error text may itself embed AMQP
  credentials** — unverified, and `mask_url_password` cannot help with a string
  this side does not compose. A later pass should check what the AMQP connect
  failure path prints before assuming masking covered it.
- **RESP3 support is display-only here**: `EXEC`/`MULTI` and pubsub were not
  touched, and nothing on the Lua side negotiates the protocol. Users enabling
  `?protocol=resp3` get correct shapes now; that is the whole scope of this
  change.

# Follow-up pass — the completion prefix (`9453189`, `3c6db22`)

This round began as a multi-return leak sweep in `poste-db.nvim` (`gsub`'s
substitution count riding into a caller's `{ … }`). Reading the completion path
to judge how far a wrong prefix could travel turned up two real defects in
`poste context detect` — the call whose answer decides which columns the popup
offers at all. Both are in the shared family binary, so the fix is here and the
specs are in `poste-db.nvim`.

## Bugs fixed

1. **An unterminated quoted identifier lost its last character, so completion
   filtered on the wrong prefix** (`tokenizer.rs` `display_text`). `"`ti` is
   what a double-quoted identifier looks like *while it is still being typed*:
   the tokenizer marks it `QuotedIdent` with no closing quote, and
   `display_text` unconditionally cut one byte off each end. `"ti` became `t`,
   which in `p."ti` means the popup offers every column starting with `t`
   instead of only `title` — and typing the closing quote is what the user has
   to do to see their own prefix honoured. The slicing is now conditional on
   the first and last bytes actually being the same quote character, so an open
   quote loses only its leading byte. Pinned first as a failing Rust test
   (`test_detect_dot_column_keeps_last_char_of_an_open_quote`).
   The CLI probe that established the defect was offset-independent: at
   byte offsets 36, 37 and 38 of the same 37-byte input the prefix came back
   `t` every time, so this was not a cursor-position quirk.
2. **A cursor on a word's right edge lost the qualifier, so a dot-column
   degraded to keywords** (`context.rs`). Editors report the caret *between*
   two tokens as the offset of the token on its right, so
   `… WHERE p.ti|, p.id` reads as "on the comma": `try_dot_column` inspected the
   comma, found no dot, and the scanner came back `Keyword` — the popup offered
   `FROM`/`WHERE` where the user was mid-word on `p.ti`. The gate is now
   strictly additive: `try_dot_column(cursor).or_else(retry from skip_back)`,
   and the retry fires only when the caret offset equals the current token's
   start *and* the previous token's end, and that previous token is a word —
   i.e. precisely the edge case. `test_detect_dot_column_reads_the_word_the_cursor_is_inside`
   covers it.
   The first draft did not do this: it recomputed the cursor *before* the single
   `try_dot_column` call, which hijacked `… WHERE u.` at offset 29 (the dot's
   left edge — already correct) and regressed
   `test_detect_dot_column_alias` to `Keyword`. That regression is why the
   shipped form retries only after the plain check finds nothing: every case
   that resolved before still resolves the same way.

## Verified this pass

- Both fixes are visible from the consumer: the two `poste-db.nvim` specs
  named "a quoted qualifier keeps its prefix filter" and "a cursor mid-line
  still reads the word it is inside" were red at HEAD and are green now, and
  they *fail* when run against a non-answering binary — which is the proof that
  they exercise the Rust path rather than passing off the Lua fallback.
- Gate after the round: `cargo test --workspace` **496 passed / 0 failed**
  (494 → +2 Rust regression tests), clippy `--workspace --all-targets -D
  warnings` 0, fmt clean. `poste context detect` on the two fixed inputs
  returns `dot_column` with `prefix: "ti"`.
- poste-db: `tests/run.sh` **1591 / 0 / 0** across 105 spec files (was
  1589 passed + 2 failed), luacheck 0 warnings / 0 errors in 245 files. The 2
  that were red were the two specs above, i.e. the round fixed pre-existing
  failures rather than introducing them; attribution used `cp` backups and a
  temporary `git show HEAD:… > file` revert of `context.lua` (restored and
  checked with `diff -q`), never a `git stash`/`checkout` that would have
  dropped the other uncommitted work.
- `3c6db22` (poste-db) removed `log.M.redact_cmd_str` — dead since `1f5ecb1`
  moved argv to a list, weaker than the live `redact_url`, and its presence
  made the log module look like it scrubbed commands it no longer sees; the
  `sql_executor_spec.lua` mock lost the matching stub key. The same commit
  parenthesized two `gsub` returns (`introspect/context.lua`,
  `ai/mentions.lua`) whose second value (the substitution count) would ride
  into any caller splicing them into `{ … }`. Those two are hazard fixes with
  no observable coverage today — no current caller splices them — which is
  worth saying rather than implying a bug was caught.

## Recorded, not changed (with rationale)

- **The right-edge retry is deliberately limited to `dot_column`.** The other
  detectors take the same cursor index, and the same "editor reports the token
  to the right" logic applies to them in principle, but only `dot_column` has
  an observed failing input. Extending a fallback to six detectors on the
  strength of one case would put six paths' existing behaviour at risk for no
  evidence. If a matching report comes in for, say, `insert_column`, the
  `or_else` shape here is the template.
- **`tests/minimal_init.lua` always resolves a binary, so "binary present" is
  not a usable predicate** — measured, not assumed: with `g:poste_binary`
  pointed at the harness dummy (an executable comment-only file),
  `sql_completion_spec.lua` runs **47 passed / 26 failed**, and all 26 are
  Rust-context tests (`get_items` seeded cache, `dot_column` alias resolution,
  `insert_column`, table context, `legacy_completion = "rust"`, the CLI
  integration block). The three `SKIP: Rust binary not found` guards in that
  file key off `find_binary() ~= nil`, which the dummy makes true, so they
  never skip — they just let the tests fail with an empty JSON decode or a nil
  item list. No false greens came out of this (that was the worry going in; the
  probe disproved it), but the failures misattribute an unbuilt sibling repo to
  the plugin under test. `state.resolve_candidate`'s own comment already
  concedes a dummy "would be picked"; the probe only shows what that costs.
  A later pass should re-key those guards on "the binary answers
  `context detect`" so a fresh checkout reports skips it can read.
- **In CI the Lua suite is advisory in both directions.** `ci.yml` checks out
  `poste-db.nvim` and `poste-ai.nvim` only — no Rust build, so CI is exactly
  the dummy case above — and the test step is
  `./tests/run.sh 2>&1 || echo "::warning::Tests failed or skipped (missing
  binary?)"`, so its exit status is discarded and no step inspects the
  `Failed :` count. Consequence worth stating plainly: a Lua-only regression
  cannot fail CI today, and cannot pass it either. Fixing that is a two-part
  change (usable-binary skips, then a real gate on the failure count) and
  belongs in the same later pass as the item above.
- The dummy itself was left alone (no non-zero exit, no stderr note). It only
  runs where no real binary exists, which locally is rare and in CI is already
  swallowed; changing its exit code is untestable here and could confuse the
  specs that treat `shell_error ~= 0` as their skip signal.

# Follow-up pass — the three doubles JSON cannot name (`08acb28`, `14ebedc`)

Went looking in the Lua DML builder, where the recorded list still carried
"`quote_literal` emitting `inf`/`nan`". The text was the symptom; the cause is
one byte of the wire format, so the fix spans both repos and the two halves
depend on each other in a way neither is safe alone.

## Bugs fixed

1. **A non-finite float column arrived as NULL** (`sql_values.rs`,
   `sql_executor/*/value.rs`, `08acb28`). `json!(f64::INFINITY)` is `null` —
   serde_json has no spelling for it, which the new
   `a_json_number_cannot_carry_infinity` test pins rather than asserts in
   prose. Postgres' `float8` really does hold `Infinity`, `-Infinity` and
   `NaN`, so every one of those cells read as NULL: the grid showed the wrong
   value, and committing a row that had one in its `WHERE` matched a different
   row than the one displayed. Fixed by one shared `float_json` that sends a
   finite double as a number and the other three as the text the engine itself
   prints — the executor converters (postgres `FLOAT4`/`FLOAT8`, mysql
   `FLOAT`/`DOUBLE`, mssql `Float4`/`Float8`/`Floatn`, the sqlite fallback) and
   the CLI converters (`session.rs`, `exec_file.rs` via `sql_values`) all call
   it, so the two families cannot drift on this rule.
2. **A committed non-finite value was written as a bare word**
   (`poste-db.nvim` `ident.lua`, `dml.lua`, `14ebedc`). `tostring(math.huge)`
   is `"inf"` and the integral test passes for it (`math.floor(inf) == inf`,
   both probed), so the `%.0f` branch emitted `SET "x" = inf`. The red run
   measured exactly that string; `inf` is not a literal to those servers, so
   the statement is an error rather than the value. Now `quote_literal` renders
   the three as `'Infinity'` / `'-Infinity'` / `'NaN'` — the quoted spellings
   postgres prints and parses — while ClickHouse keeps the bare `inf` / `nan`
   it spells as literals itself, which is what the old code already sent.

The order matters: fix 1 on its own would *open* fix 2's path, because the cell
text became `"Infinity"` and LuaJIT's `tonumber` accepts that spelling
(`parse_value("Infinity")` returns a number, now pinned by a spec in
`sql_editor_spec.lua`). Both halves are in this pass for that reason.

## Verified this pass

- LuaJIT probes, in the plugin's own interpreter: `string.format("%.0f",
  math.huge)` = `inf`, `math.floor(inf) == inf` = true, `tostring(0/0)` = `nan`,
  `tonumber("inf")` and `tonumber("Infinity")` both = `inf`,
  `math.abs(inf) == inf` = true.
- Rust: the serde_json premise test above, plus a test per spelling and one that
  finite doubles (including `-0.0` and `f64::MAX`) stay numbers, so the fix is
  not a blanket "floats become strings".
- `sql_executor/sqlite.rs` gained the only end-to-end check available without a
  server: an in-memory SQLite, a `REAL` column holding `9e999`, converted
  through the executor's own `sqlite_value_to_json` — `Infinity`, `-Infinity`,
  `1.5`. It also proves the wiring, not just the helper: the mutation below
  reached it.
- Mutation proofs. Neutering `float_json`'s finite/infinite split (`is_finite`
  forced true) turned 3 Rust tests red — the two spelling tests and the SQLite
  end-to-end one — while `float_json_leaves_finite_doubles_as_numbers` stayed
  green. On the Lua side, `is_non_finite` → `false` turned 3 specs red (1 ident,
  2 dml) and dropping the ClickHouse carve-out turned 2 red (one per file).
  Restores verified byte-identical with `diff -q`.
- `sql_values.rs` and `sql_executor/*/value.rs` are still two converter
  families; only `float_json` is shared. Left as is: unifying them is a real
  refactor, and the drift that actually bit here was one rule, not the layout.
- Not measured: any of this against a live server. The specs assert emitted SQL
  text and JSON values; "postgres parses `'Infinity'` back to the value it
  prints" is the documented spelling it uses for input and output, and
  ClickHouse's bare `inf` is preserved behaviour rather than a new claim.
- MySQL cannot store an infinite `DOUBLE` in the first place, so its branches
  matter for `sql_values` symmetry, not for a user-visible case.
