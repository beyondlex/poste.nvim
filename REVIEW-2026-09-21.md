## Bugs fixed

1. **`port` was never expanded, and barely validated** (`sql_connection.rs`,
   `f2a5948`). The store parsed `port` with `u16::try_from` at load time and
   then substituted `{{VAR}}` references into host/user/password/database/path
   — not `port`. Lua's `apply_env` substitutes *every* field before validating
   any of them, so `port = "{{DB_PORT}}"`, a config the editor honours, lost
   its value here and connected to the dialect default; `port = 0` fitted a
   `u16` and reached the URL as `…:0/…`. `port` now keeps its raw text
   (`ConnectionConfig::port_raw`) whenever it is not already a usable number,
   and `parse_port` accepts exactly what Lua's `tonumber` + integrality +
   1..65535 check accepts (`"5432.0"` in, `"5432.5"`, `"abc"`, `0`, `70000`
   out). An unparseable value fails *that connection* at resolve with the
   message naming it — the Lua resolver scopes it the same way, and one typo'd
   stanza taking down every other entry in a shared file would be the worse
   bug. The value stays out of the message: `port = "{{POSTE_PASS}}"` is a
   plausible typo and this reaches a terminal.

2. **Two hand-copied substitution lists** (`ConnectionStore::resolve` and
   `poste-cli/src/connection.rs`'s `connection test`). Identical five-line
   blocks, and the drift that the duplication invites had already happened in
   the one direction that mattered: neither list included `port`, so
   `connection test` would have checked the default port even after `resolve`
   was fixed. Both now call one `ConnectionConfig::with_vars_resolved`, which
   returns the resolved config (so `test` can hand it to `test_connection`) or
   the port error.

3. **The legacy `connections.json` accepted port 0** (`sql_connection.rs`,
   `82cc1c4`). There `port` is a serde-typed `u16`, so `70000` and `"abc"`
   failed the load but `0` passed straight into `mysql://h:0/`. The load now
   defers it to the same resolve-time check the TOML path uses, so both files
   answer a bad port identically: an error naming the connection.

  Lua `build_conn_url` (percent-encode sets, alias tables, auth shapes,

## Recorded, not changed (with rationale)

## Round 2 — the CLI's URL rules and statement classification

Same day, second pass, upstream-to-downstream this time: how a resolved
connection URL is *read* (`exec-file`, `session`, `introspect`), what those
paths print when they cannot read it, and how a statement is classified.
Baseline for the round: 483. After: **487 passed / 0 failed**, clippy
`--workspace --all-targets` 0 warnings, `cargo fmt --check` clean.

4. **Three copies of the URL-scheme rule, already drifted, and `mariadb://`
   in none of them** (`poste-core/src/request.rs`, `a3ea26b`). `exec_file.rs`,
   `session.rs` and `introspect.rs` each hand-rolled the same
   `starts_with` chain. They disagreed on the failure mode — exec/session
   bail, introspect answered `"postgres"` for *anything* it did not recognise,
   including a `redis://` URL, which then died inside the postgres driver with
   a message about a URL that never claimed to be one. Worse, Lua's
   `constants.URL_SCHEMES` (whose own comment names these three chains as its
   mirror) lists `mariadb://`, and sqlx's MySQL driver lists it too
   (`URL_SCHEMES = ["mysql", "mariadb"]`), so a legal
   `url = "mariadb://…"` entry was readable by the editor for display and
   session context yet failed the moment it ran. The chain is now one
   `Protocol::from_sql_url`, extended to cover `mariadb://`, with the three
   entry points calling it and introspect's silent postgres fallback removed.

5. **Every "cannot determine protocol" message printed the connection
   password** (`7d8984c`, `ba31fd1`, and the redis/mq/mssql/clickhouse
   validators). The CLI's `mask_url_password` was private to the `connection`
   subcommand, so the six other places that quote a resolved URL in an error —
   exec-file, session, introspect, the redis and AMQP validators, the mssql
   and clickhouse URL parsers — echoed it raw. Those URLs carry real
   credentials by construction, and a CLI error line reaches a terminal,
   `:messages`, and saved result files. The helper moved to `poste-core`
   beside the other URL rules and every one of those sites masks now.
   Moving it fixed a second defect: it scanned for `@` across the whole URL,
   so `postgres://db.example.com:5432/team@billing` — `@` is legal in a
   database name — lost its port and part of its name to the mask while
   hiding nothing. The scan is confined to the authority now, which the new
   test pins in both directions.

6. **A truncated redis string still shipped its full parsed body**
   (`redis_executor.rs`, `4d8a18d`). `max_bytes` cut `value`, then the JSON
   heuristic parsed the *untruncated* string and attached the whole document
   as `parsed`, so one large JSON value defeated the cap and re-appeared in
   stdout — the size class these caps exist to bound, because the Lua side
   reads line-delimited JSON and an oversized line stalls the job. `parsed` is
   now emitted only when the value fit. No consumer reads the field today
   (checked across all three Lua plugins), so the shape change is invisible
   except for the huge-value case.

7. **`RETURNING` matched as a substring, unlike the Lua mirror**
   (`sql_exec_common.rs`, `cca0b81`). `exec_run.lua` has used a
   `%f[%w_]returning` word-boundary test since it hit this exact case, and its
   comment names `my_returning_col`; the Rust copy kept
   `upper.contains("RETURNING")`. So `UPDATE orders SET returning_flag = 1`
   took the fetch branch: `fetch_all` runs the statement, but the outcome is
   reported with `is_dml: false, affected: 0` — an update that changed five
   rows displayed as "0 rows". Classification now matches whole words.

  `const.default_port` does *not* normalize aliases, so `dialect = "postgresql"`
  would have reached `.. ":" .. port` as nil and thrown — except every entry
  point into `build_conn_url` (`get_connection_config`, `resolve_connection_url`,
  `name_for_url`, `list_connections`) applies `normalize_dialect` first, and the
  display fallback at `connections.lua:458` is fed the same normalized values.
  Confirmed by reading all four, not by the port table passing.
- The Rust/Lua percent-encoding sets agree: `USERINFO_ENCODE_SET` is CONTROLS
  plus every printable ASCII outside `A-Za-z0-9-._~`, i.e. the same RFC 3986
  userinfo rule the Lua encoder implements.
- `sql_ddl`'s `create_table` is the only member with a production caller (the
  four `sql_introspect` modules), and the two dialects whose `column_def_sql`
  ignores `comment`/`extra` (mssql, clickhouse) both pass `None` for those
  fields, so the silent loss is unreachable today. Documented in the code

## Recorded, not changed (with rationale)

- **Six `DdlGenerator` members have no caller** (`add_column`, `drop_column`,
  `rename_column`, `alter_column_type`, `add_index`, `drop_table`): they exist
  since the initial commit as table-designer scaffolding, are exercised only
  by their own tests, and the browser's column actions build their ALTER SQL
  in Lua instead. Two of them are also subtly wrong — `add_column` routes
  through `column_def_sql`, so a caller that sets `comment` loses it on every
  dialect. Deleting them is the right call the next time this file is touched
  for a real reason; deleting them now would also delete the only tests that
  document each dialect's ALTER syntax.
- **Three copies of the default-port table**: `Dialect::default_port` (zero
  production callers), `ConnectionConfig::to_url`'s inline match (the live
  one), and Lua's `DIALECT_DEFAULT_PORTS`. All four values agree today, and
  `to_url`'s `_ => 1433` arm is only reachable for `mssql` because the outer
  match names the other three — adding a fifth network dialect there would
  silently inherit MSSQL's port. Worth collapsing onto `Dialect::default_port`
  when a dialect is actually added.
- **`introspect` now fails on an unknown scheme** instead of assuming
  postgres. Deliberate, and it only changes the message for inputs that were
  already broken.
- **`--max-items 0` renders nothing** rather than meaning "unlimited" the way
  `--max-rows 0` does. Lua never passes 0 (it either omits the flag or sends a
  positive cap), so the two zero-means differ without ever meeting.

## Round 3 — the rules Round 2 introduced, applied to their inputs

Third pass the same day, and the theme was that fixing a rule's *location*
exposes its *content*: two of the three copies this round are the mask and the
dialect table that Rounds 1–2 collapsed onto a single function. Baseline 487.
After: **496 passed / 0 failed**, clippy `--workspace --all-targets -D
warnings` 0 warnings, `cargo fmt --check` clean, and the exec-file goldens
byte-identical (so the dialect-label de-duplication and the status cap changed
no existing wire output).

8. **The password mask hid the wrong bytes in two shapes** (`request.rs`,
   `1a6225a`). Round 2 confined the `@` scan to the authority, which fixed
   `team@billing` and immediately broke the opposite case: a password
   containing an unencoded `/` has its `@` *after* a path separator, so it
   printed in full. The other half was older — userinfo split at the **last**
   colon, so `postgres://u:pa:ss@h/…` printed `u:pa:****`, leaking the `pa`
   prefix; a URL parser splits at the first colon, which makes everything
   after it password. Both are reachable only through a raw
   `url = "…"` entry: `to_url()` percent-encodes user, password and database
   with everything outside RFC 3986's unreserved set, so a field-form URL can
   not contain a bare `@`, `:` or `/` in userinfo at all.
   The scan is two-step now — the authority decides whether there are
   credentials, and a `@` past the first `/` is honoured *only* for an
   authority that already looks like credentials (`user:secret`, not
   `host:5432`, so `[::1]:5432` still reads as a host and `/team@billing`
   still loses nothing). `docs/schema.md` rule 5 states it, and one fact in
   the comment is a non-goal: Lua's `redact_authority` deliberately scans
   wider, because it is fed arbitrary log text rather than a URL and there
   over-redacting is the safe error.

9. **`--max-bytes` capped `value` but not `status`** (`redis_executor.rs`,
   `d28c5d7`). A string reply put the whole payload in the `status` field
   verbatim, so `GET` of a large key under `--max-bytes 64` measured 5000
   bytes on the line the Lua job contract reads one-object-per-newline — the
   exact stall class `4d8a18d` bounded for `parsed`. `value` and `status` now
   share one `cap_bytes` (same char-boundary walk-back, one copy), and
   `redis_value_to_json`'s BulkString arm calls it instead of inlining the
   loop.

10. **A rejected `COMMIT` was invisible** (`exec_file.rs`, `d61386e`). All
    four transaction-capable dialect paths ended `--mode transaction` with
    `.ok()` on the COMMIT. A commit the server refuses (deferred constraint,
    a dropped connection, a full disk) rolls the *whole batch* back, and the
    stream still said "N statements succeeded / failed: 0" — the one failure
    that invalidates every line above it was the only failure with no channel
    to the UI. `record_commit` now emits the statement-shaped error event
    (`sql: "COMMIT"`) that `exec_run.lua` already counts into `has_error`.
    The rollback sites keep swallowing, deliberately: that error is
    secondary to the statement failure already reported.

11. **A fifth copy of the protocol → dialect-name list, in the one place that
    publishes it** (`exec_file.rs`, `5bd23bf`). The summary event's `dialect`
    is the string the Lua renderer keys on; it now comes from
    `sql_dialect::dialect_for`, like introspect's. Goldens pin the value, so
    this is a pure de-duplication.

12. **The splitter did not know MySQL reads `\'` as an escape**
    (`sql_parser.rs`, `1699d62`). `mysqldump` writes an apostrophe inside data
    as `\'`, which is what MySQL's default `sql_mode` means; the splitter only
    knew `''` doubling. So `'it\'` closed the literal, the next quote opened
    another, and every `;` after it landed inside a string — the rest of the
    file folded into one statement. `QuoteEscapes::{Standard, Backslash}` now
    says how a dialect reads a backslash, chosen from the protocol at both
    entry points (`exec-file` and `parse_sql_request`), and `QueryKinds`
    carries it so classification blanks quotes the same way the splitter did.
    It is per-dialect on purpose: `SELECT 'C:\'; SELECT 2;` is two statements
    in postgres/sqlite/mssql/clickhouse and one under the MySQL rule — the
    same failure running the other direction. Backticks are a quoted
    identifier everywhere now too (`SELECT \`a;b\`` split in half before).

13. **The redis winbar printed the transport cap as the value's length**
    (poste-redis `format.lua`, `7caaa44`). `status_summary` measured
    `#value`, i.e. what the binary was willing to print, so a 50 MB string
    read "len 65536" and looked complete. `len` is authoritative; when it
    exceeds what is shown the summary says "len N, truncated" — the fact the
    grid already displays.

## Verified clean rather than assumed

- The mask's residual gap is narrow and self-limiting. For step 2 to decline,
  the userinfo's password must be all ASCII digits *and* contain a raw `/`, so
  `postgres://u:123/456@h/db` reads as host `u`, port `123` and stays
  unmasked — but that is exactly how a compliant parser reads it too (it
  connects to host `u:123`, database `456@h`), so the URL was never going to
  authenticate as intended. Closing the gap means guessing which side of a
  `/` is the password, and the ambiguity is not worth it for a form the field-
  based writer never emits.
- The two `@`-scanning implementations were compared line by line (Rust
  `mask_url_password`, Lua `redact_authority`): both split userinfo at the
  first colon, both require a non-empty secret, and the specs in
  `tests/sql/sql_log_spec.lua` already pin the Lua side's slash-password and
  `?user=a@b` cases, so the divergence in 8 is a documented difference in
  input shape rather than drift.

## Recorded, not changed (with rationale)

- **mq-exec has no wire caps at all** — no `--max-items`/`--max-bytes`, and
  `delivery_to_message` (`mq_executor.rs:278`) labels every payload
  `payload_encoding: "string"` after a lossy UTF-8 pass, duplicating it as
  `payload_json`. Binary AMQP messages therefore arrive mangled and a large
  body arrives unbounded, but the field is a cross-repo contract with
  poste-mq.nvim, out of this review's three-repo scope.
- **`NO_BACKSLASH_ESCAPES`** flips MySQL back to the standard rule, which the
  `QuoteEscapes::for_protocol` choice (keyed on the scheme, not the session's
  sql_mode) gets wrong for that mode. The default is the escape form, so the
  fix helps the overwhelming case and `mysqldump` output is the common input;
  a per-session sql_mode probe is not worth a second round-trip per file.
- **`exec_*` functions in `exec_file.rs` take 13 arguments**, four of them
  `&mut` counters threaded through every dialect path, each under
  `#[allow(clippy::too_many_arguments)]`. That is an execution-context struct
  asking to exist, and it is the reason `record_commit` needed a helper at all
  (four sites, four counter borrows). Worth one refactor when a dialect is
  actually added; the goldens make it a mechanical change.

## Round 4 — the second and third scanners, asked the same questions

Round 3 fixed the file splitter's quoting; this round put the same questions to
the completion tokenizer and the scope resolver, which read the same bytes for
the cursor. Baseline 496. After: **536 passed / 0 failed** (+40), fmt and
clippy clean. The theme repeated itself immediately: three scanners, three
ideas of what a quoted run is.

14. **The tokenizer had its own, narrower idea of a quoted run**
    (`sql_context/tokenizer.rs`, `ad9ec7a`). Only `$$` opened a Postgres dollar
    quote, not `$tag$`, so a function or `DO` body was tokenized as SQL and a
    `;` inside it ended the statement: `context stmt-ranges` cut
    `CREATE FUNCTION … $fn$ … $fn$` in half and offered the tail of the body —
    `END`, `$fn$ LANGUAGE sql` — as a statement to run, which is precisely the
    text the splitter keeps together. And `"` and backtick runs stopped at the
    first inner quote, so `"my""table"` became two identifiers and the
    completion lookup asked for a table named `my`; `''` doubling was already
    handled for strings, and the same rule belongs on every quote character.
    All three runs share one `scan_quoted` now; `$1` and a tag without its
    closing `$` stay ordinary characters, matching the splitter's grammar.

15. **The tokenizer did not know MySQL reads `\'` as an escape either**
    (`bd347d1`). Round 3's item 12 taught the splitter; completion asks the
    same "where does this literal end" question and had nothing. On a
    mysqldump-style file the consequence is not cosmetic: `'it\` closes the
    literal, the next `'` opens one with no partner, and everything after it
    arrives as one string — so `context detect` reports `in_string` and offers
    nothing for the rest of the block, and the table list loses its FROM
    target with it. `tokenize_with` now takes the same `QuoteEscapes` the
    splitter takes, derived from the `--dialect` the editor already passes.
    Postgres' `E'…'` needs no dialect at all (the prefix is the literal opting
    in) and is handled under every reading, with an `e` that ends a longer
    identifier excluded (`name'x'` is not a prefix).

16. **Every subquery completed against the outer query's tables**
    (`sql_context/scope.rs`, `c0ec467`). The resolver flattened the statement's
    top-level FROM list, so a cursor inside a subquery, derived table or CTE
    body was offered the outer columns — or the derived alias itself — and
    never the relations it was being typed into. One scope frame per paren
    level now, resolved innermost first together with its ancestors: sibling
    subqueries keep separate frames, a closed subquery still cannot leak into
    the outer query, and an unmatched `)` no longer drives the depth counter
    negative and hides every later FROM list.

17. **`SELECT … UNION SELECT …` was two statements** (`statements.rs`,
    `4489862`). `context stmt` and `stmt-ranges` split per arm, so the Rust
    fallback for "run statement" executed only the branch under the cursor — a
    different result set, with no error to show for it. A statement-start
    keyword preceded, at the same paren depth and optionally by one `ALL` /
    `DISTINCT`, by a set operator is a branch head, not a boundary; the
    predicate lives in the tokenizer so the scope resolver and the statement
    scanner cannot answer the question differently. `MINUS` stays out
    deliberately (Oracle-only; treating it as an operator would merge
    statements for everyone else). This commit shipped no test of its own — the
    range assertions arrived one commit later, in `de48131`, which is why the
    tally below counts them once.

18. **A UNION arm inherited the previous arm's tables, and a comma list
    registered one element** (`de48131`). With item 17 making the arms one
    statement, the frame resolver had to keep them apart: a set operator now
    pushes a frame, so `x` is no longer referenceable from
    `… FROM x UNION ALL SELECT b FROM y WHERE ▮`, while `WITH` names sit
    outside that prefix and stay visible across the arms. Separately,
    `FROM a, (SELECT 1) AS d, public.logs` registered only `a`, and
    `generate_series(…) AS g` exposed nothing but a stray paren element;
    `register_table_list` walks the comma elements, skips `LATERAL` / `ONLY`
    qualifiers, and starts its alias lookup *after* the `AS` token. Three
    hand-rolled paren-depth walks collapsed into `matching_rparen`, which also
    stops an unmatched `)` from popping the top-level frame.

19. **The cursor one past the last character read as a different token**
    (`context.rs`, `865270c`). In `SELECT alias.col▮` the editor reports the
    offset after the word and the tokenizer opens the *next* token there, so
    `alias.col` kept its column context only at end of buffer — the most common
    mid-word position in a SQL file fell back to the generic keyword menu. A
    flush cursor is now read as the identifier it follows (`.` and `(` already
    read forward). `UPDATE … SET col▮` returned keywords, so the assignment
    list of the statement most often edited in a buffer never offered a column;
    the token before the cursor decides now. `ON DUPLICATE KEY UPDATE col▮` and
    `REFERENCES tbl▮` needed the same relation/column split behind one
    `is_upsert_update` probe rather than two copies, and `DO UPDATE SET` stopped
    registering `SET` as a table — a clause keyword cannot start a FROM element.

20. **Typing a quoted name lost its last character** (`tokenizer.rs`,
    `74db519`). While `"p"."ti▮` has no closing partner the token ends on the
    last typed character, and `display_text` stripped it as if it were the
    quote: the prefix came back one letter short (`left: "t"`, `right: "ti"`),
    and after a bare `"p".` it came back as a quote, which filters every
    column away and leaves the menu empty. The trailing byte is stripped only
    when it closes the token. This was a two-sided bug: poste-db's
    `handle_dot_column` re-derived the prefix from `line_before` with
    `[%w_]+%.([%w_]*)$` — a second, narrower copy of the rule that cannot see a
    quoted qualifier — and filtered on an empty string, listing the whole table
    (`d8e30ce`); it now uses `rust_ctx.prefix` and keeps the Lua pattern as the
    fallback for when no Rust context exists.

21. **The SQLite function menu dropped everything MySQL shares with it**
    (`functions.rs`, `29af755`). `MYSQL_ONLY` was read as "not in Postgres
    *and* not in SQLite", so `hex`, `unhex`, `instr`, `ifnull`, `group_concat`,
    `char` and the `json_set` family — all plain SQLite functions, checked
    against SQLite 3.51 — never appeared in a SQLite buffer. They moved to a
    new `NOT_PG` list that only the Postgres filter reads, `SUBSTR` left the
    exclusions (all three dialects have it), and a list-consistency test now
    fails a name that filters nothing, or one that filters a whole menu away.

22. **`$POSTE_BINARY` never reached the process that needed it** (poste-db
    `state.lua` `6227caf`, poste-redis `state.lua` `eb1fc20`). plenary runs each

    in `tests/minimal_init.lua` applied only to the parent: inside the child no
    binary was found, and every Rust-dependent assertion failed on an empty
    completion list (14 red in `sql_completion_spec` alone) or printed SKIP
    *while the file reported success* — the quietly worst kind of gap, because
    it made the completion specs read as passing. An environment variable is
    the one channel the child inherits, so the resolver reads `vim.g` →
    `$POSTE_BINARY` → `$PATH` and the bootstrap exports what it picked. The
    redis copy had drifted the other way too: it tested `filereadable` alone, so
    a file without the exec bit — a downloaded binary, the test dummy — won over
    a working `poste` on `PATH` and then failed at spawn with an opaque error.
    Both now share the same `usable` predicate.

## Recorded, not changed (with rationale)

- **`MINUS` is not treated as a set operator.** Oracle's spelling of `EXCEPT`;
  calling it one would merge two statements for every dialect where it is an
  identifier or a function name. Documented at the predicate.
- **Every `context detect` answer carries the dialect's whole function menu**
  (`known_functions()` is 258 names; the filters leave each dialect with
  ~170) although two Lua handlers read it, so a plain table-name context pays
  about 2 KB per request. Prefix-filtering server-side changes the wire shape
  for a rounding error in latency — the array is `&'static` and cloned once.
- **Scope frames are text, not catalog.** A CTE name and a derived-table alias
  enter as virtual relations with no schema, so a CTE that shadows a real table
  can offer the wrong columns. Closing that needs an introspection round-trip,
  and the completion path is deliberately round-trip-free.
- **Quoting is per-dialect; keyword classification is not.** `escapes_for` is
  the only place the tokenizer consults the dialect, so `is_column_keyword` and
  the statement-start table are shared across all of them. A clause keyword that
  belongs to one dialect only — mssql's `TOP`, absent from the table — reads as
  a plain identifier everywhere, which is the conservative direction (an extra
  candidate in a menu, not a missing one). Splitting the tables is a word list
  per dialect, worth doing when one of them actually bites.

## Round 5 — the CLI's env, directive and session boundaries

Fourth pass over the same three repos, on the boundary the plugins hand to the
binary: how a URL gets its variables, how a file picks its connection, and what
a session owes a request. Baseline 536. After: **550 passed / 0 failed** (+14),

23. **A `{{var}}` inside a value was expanded exactly once** (`env.rs`,
    `c69849b`). `substitute_vars` made a single pass, so
    `"INNER": "{{BASE}}.example.com"` reached the driver with the inner
    reference still spelled out, while poste-db's Lua copy — which recurses,
    capped at 10 rounds — connected. It now loops to a fixed point under the
    same cap, so a self-reference ends unresolved instead of either expanding
    forever or vanishing. Probed end to end through
    `poste connection list --path /tmp/envprobe --env dev`: before
    `postgres://{{BASE}}.example.com:5432/d`, after
    `postgres://db1.example.com:5432/d`.

24. **One JSON number deleted every variable** (`poste-cli/src/util.rs`,
    `5c31b7d`). `load_env_vars` deserialised `env.json` into
    `HashMap<String, String>`, so `"PORT": 5432` — the natural thing to write in
    a JSON file — failed the whole document, and every `{{VAR}}` in the
    connection stayed literal. The reader now parses to `serde_json::Value`,
    takes `envs` or the top level (Lua's `parsed.envs or parsed`), selects the
    requested environment, and keeps string/number/bool while skipping objects
    and null: one structural entry can no longer hide the names beside it. Same
    probe with a numeric `PORT`: before `postgres://{{BASE}}:5432/d`, after
    `postgres://h1:5432/d`.

25. **The `@connection` directive had four copies, and two of them accepted
    text the user did not mean as a directive** (`exec_file.rs` `2d99313`,
    poste-db `ai/actions.lua` `da632fa`, `file_exec.lua` `f5357c1`). The CLI
    searched each line with an unanchored pattern while
    `strip_sql_directives` — which decides what stays in the SQL body — is
    anchored, so `SELECT 1; -- @connection postgres://…` chose which database
    the file ran against and stayed in the statements (before the fix the
    resolver answered `left: Some("postgres://stray:pw@h/db")` for exactly that
    file). The AI header suppression had the same shape one repo over: an
    unanchored `text:match` meant a `'-- @connection other'` inside a string
    literal or a prose comment skipped the header, and the block then ran
    against whatever connection the buffer had rather than the chat scope's
    bound one. Both sides now read one anchored rule — `extract_connection_directive`
    / `strip_sql_directives` in Rust, `constants.match_directive` in Lua, which
    is the fourth copy's deletion — the Lua specs assert the shapes the Rust
    test rejects, and `docs/schema.md` carries the pattern as rule 6 so the
    next drift is a written-down violation.

26. **A redis session request could be dropped without a reply**
    (`redis_session.rs`, `f296ca9`). The loop built its tokens with
    `filter_map(as_str)` and skipped the request when the result was empty. Two
    consequences: `["SET","k",5]` ran `SET k` — a non-string element vanished
    rather than being rejected, so a numeric argument became a different write,
    and `["SCAN",123,…]` resumed from the wrong cursor — and an empty command
    got no answer at all. poste-redis registers its pending callback before
    `chansend` and clears it only on a send failure, so that request hung until
    the stall watchdog restarted a perfectly healthy session. `request_tokens`
    now rejects a missing or non-array `command`, any non-string token, and an
    empty command, each answered with an error event carrying the request's own
    seq.

27. **… and a reconnect retried the command on the wrong database**
    (`f284765`). The tracked `SELECT` was restored with `let _ = …`, so a
    restore that failed — or hung, the one unbounded await in a loop otherwise
    built never to hang — was discarded and the command re-ran on database 0
    while the buffer header still named db N. That is the same silent wrong-db
    hazard `session_conn.lua` refuses on the steering path; the binary now
    bounds the restore by `RECONNECT_TIMEOUT` and returns its failure as the
    request's error reply. No broker in this environment (`REDIS_TEST_URL`
    unset skips the integration specs), so this one is verified by inspection
    and has no red test to quote — recorded rather than papered over.

28. **An AMQP consumer could name no queue** (`mq_session.rs`, `64e8fba`).
    `queue.unwrap_or_default()` reached `basic_consume("")`, which AMQP answers
    by minting a *server-named* queue: the request reported ok, the tail waited
    on a queue nothing publishes to, and the broker kept the object for the
    session's lifetime. `"ack": "yes"` (a string) read as `false`, so a tail the
    user asked to consume-and-remove stayed in requeue mode — the messages come
    back to the queue when the tail stops, which is the safe direction but not
    the one the caller chose, and nothing on the wire said the flag was ignored.
    Both are rejected now with an error carrying the request's seq, naming the
    field and not the offending value; `stop` reports whether a consumer was
    actually torn down instead of always `stopped: true`.

## Recorded, not changed (with rationale)

- **`mq-session`'s operation timeout is an inline 30 s**
  (`mq_session.rs:284`), while redis-session has named `COMMAND_TIMEOUT` /
  `RECONNECT_TIMEOUT` — and no flag reaches either (mq-exec has no timeout flag
  at all). A slow broker cannot be given a longer leash without a code change;

  statement of intent rather than edited into all five loops.

  (`"nullable": type != "BOOL"`). Re-verified two ways: sqlx 0.8.6 exposes no
  runtime nullability (no `nullible` / `is_nullable` anywhere in sqlx-postgres
  or sqlx-core), and no consumer in either plugin repo reads the field. Deleting
  it is a MAJOR wire-shape change under `docs/schema.md`, so it stays recorded
  with its 09-16 entry rather than removed quietly.
