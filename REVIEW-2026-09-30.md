## Probed through the real binary, held

These back contracts the sibling Lua repos code against; both probes
ran against a live local `redis-server` on the debug build.

- **A failed SELECT leaves the connection on the old db.**
  `SELECT 5` → OK, `SELECT 999` → `ResponseError: DB index is out of
  range`, next `PING` answered on db 5. `session_conn.lua`'s revert
  (`session.db` back to the old value, SELECT re-issued next execute)
  is correct only while the binary keeps this behavior — if a driver
  change ever makes a failed SELECT switch anyway, the Lua side will
  believe the wrong db with no error anywhere. Recorded on both sides.
- **Hostile session stdin never desyncs the loop.** Duplicate seqs are
  echoed verbatim; a request with no `command` array errors *with its
  seq*; a line that is not JSON errors with seq `0` — which no Lua
  pending slot can occupy (seqs start at 1); an empty command array
  errors. Every later request still answered.
- **`--max-items` truncation carries `truncated: true` plus the real
  `len`** on list/zset replies — the shape the redis browser's
  `DEFAULT_MAX_ITEMS = 100000` relies on to keep silent truncation out
  of SCAN paging.
- **The SCAN cursor is still a JSON string** (`"cursor":"0"`), keys
  under `value.value` — the round-16 pin holds on today's build.
