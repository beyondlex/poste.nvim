## Fixes (each with tests)

- **A zero-row query arrived with `columns: []`.**
  `sqlx_rows_to_block` read the column metadata off `rows.first()`, which
  does not exist when nothing matched — `SELECT * FROM t WHERE x > 99`
  executed fine and reached the consumers shapeless: the Lua grid could not
  even render an empty table head, unlike psql or every driver UI. On the
  zero-row path the statement is now `describe`d and the columns recovered;
  the extra round-trip only fires there, and a describe failure keeps the
  old shape instead of failing a statement that already succeeded.
  `run_sqlx_statement` now takes the executor as `&'e mut E` with a
  `for<'c> &'c mut E: Executor<'c>` reborrow bound so it can be used twice
  (fetch_all, then describe) — call sites unchanged. DML statements still
  report `columns: []`, which is correct: they have no resultset.

- **A leading UTF-8 BOM blinded classification and the directive regex.**
  Windows editors and PowerShell's `Out-File` write a BOM by default, and
  Neovim keeps U+FEFF in the buffer with `'bomb'` off — so a BOM'd `.sql`
  reached the splitter glued to the first keyword:
  - `\u{FEFF}SELECT 1` was classified as DML and executed through the
    no-rows path: "Query OK", resultset silently discarded (verified live:
    sqlite skips the BOM, so the statement *ran* — the binary just threw the
    rows away).
  - `\u{FEFF}-- @connection …` was not a directive line (`\s` does not
    match U+FEFF), so the connection hint was missed.
  `strip_directives` and `split_statements_with` now strip a leading BOM,
  and the SQL session transports strip it off each request's `sql` in
  `parse_request` (the session loops share it; redis-session parses token
  arrays, and its file-side BOM is handled by poste-redis's parser fix this
  round). `docs/schema.md` records both the BOM strip and the zero-row
  columns contract.

## Verified clean rather than assumed

- **CRLF line endings** in a `.sql` file: statements split cleanly, the
  echoed `sql` carries no stray `\r`, keyword classification unaffected.
- **The echoed `sql` keeps string literals** (`VALUES ('x', 1)` round-trips
  into the events) — a probe first suggested otherwise, but the file itself
  had been mangled by shell quoting; od on the input settled it.
- **`--max-rows 0`** stays unlimited end to end (pinned by the existing
  truncation test's non-zero path and probed here).
